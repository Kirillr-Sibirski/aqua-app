## 0. Verdict in one paragraph

The KB is unusually strong on protocol internals (fork tests that pass against the canonical registry, exact selectors, opcode tables, byte layouts), hackathon rules and winner patterns. Its weaknesses are (1) **staleness drift**: three files still say "UNCERTAIN which router is deployed" while four others verified it; (2) **one undocumented ABI split** that silently breaks the "Extruction against the official router" path; (3) **feasibility blind spots** in the position catalog (EIP-170 size limit of the full opcode set, no fixed-point math library in the tree, effort estimates of 8-16 h against a 10-hour build); (4) **demo-path de-risking** is incomplete for anything that is not a Foundry test (oracle mocking from a script/UI, swapping against live makers, KycNFT gate); (5) a handful of **human logistics unknowns** (team track, check-in) that expire within 48 h. None of these invalidates the KB; all are fixable with the tasks in §2.

## 4. Overall assessment for the design workshop

**Strengths to lean on.** (a) Two independent, passing fork proofs that a *modified* HEAD router works against the official registry (`customrouter-example/test/ForkOfficialAqua.t.sol`, `mywork/test/MyRouter.t.sol`) — the build can start from those today. (b) Complete, cross-checked HEAD instruction semantics with ordering rules and a verified custom-opcode template (~150 lines incl. tests). (c) Verified fork recipe (Base, Tenderly gateway, whales, Aave, Chainlink addresses, `--load-state` for a fixed router address). (d) Clear judge taste: every recent 1st-3rd shipped a custom instruction + fork/testnet fills + real tests; UI-only and NL-composer projects lost. (e) Market/competitor material is more than enough for the pitch.

**What the workshop must not assume.** (1) That the official router accepts HEAD-style Extruction targets (G1). (2) That any subset of opcodes fits in one router (G2). (3) That oracle-driven positions can be demoed from a UI without a mocking recipe (G4). (4) That the catalog's effort numbers (8-16 h for #1-#3) fit a **10-hour** build — realistically one custom opcode (≤ 200 lines), one fork script proving fills, `CoreInvariants` run, and either a minimal UI or a `forge` demo; the "Liquidity OS"/JIT-lending/RMM-01 headline ideas need scoping down or a second person. (5) That gas/size for fractional-power curves is known (G6).

**Cheapest high-signal moves the KB already supports.** Swap against a *live ungated Base strategy* via the official router, then ship our own strategy to our router against the same registry (G3) — this single script proves rules 1 and 2 and demonstrates "one wallet, many strategies". Use the `Simulator`/`asView().quote` path in the UI; use `Salt` per strategy; keep `evm_version=cancun`, via_ir, 700 runs.

**Ranking of gaps by expected impact on the *choice* of idea:** G2 (size) and G6 (math) constrain which curves are buildable; G1 and G3 decide the "official router" narrative; G4 decides whether oracle ideas are demoable; G5 only if a UI on HEAD is chosen; G7/G8/G9 are hygiene but G9 has a hard date (Sep 7).
